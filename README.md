# Календарь звонков


[![hexlet-check](https://github.com/DrPrimus/ai-for-developers-project-386/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/DrPrimus/ai-for-developers-project-386/actions)

Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Сценарии

### Сценарий владельца календаря

1. **Создание типа встречи**: Владелец создает новый тип встречи, указывая название (например, «Консультация»), описание и длительность (например, 30 минут или 1 час). После сохранения тип встреча появляется в списке доступных вариантов для гостей.

2. **Просмотр предстоящих встреч**: Владелец видит список всех **запланированных** встреч любых типов на ближайшие 14 дней. Список обновляется при каждом новом бронировании гостем. Содержит дату, время, тип встречи.

### Сценарий гостя

1. **Вход без регистрации**: Гость открывает приложение и попадает на главную страницу — витрину сервиса. Регистрация не требуется — доступ гарантирован через гостевой режим. Кнопка «Записаться» ведёт к выбору типа встречи.

2. **Выбор типа встречи**: Отображается список типов встреч, созданных владельцем. Гость выбирает подходящий вариант (название и описание). Выбранный тип определяет длительность будущего слота.

3. **Открытие календаря на 14 дней**: После выбора типа встреча гостю открывается календарь, охватывающий текущую дату и следующие 13 календарных дней (всего 14 дней с сегодняшнего дня). Доступные слоты подсвечиваются в соответствии с часами работы владельца и часовым поясом, заданными как константы.

4. **Поиск свободных слотов**: Календарь показывает доступные временные интервалы в выбранную длительность. **Слоты отображаются в виде блоков**, которые гость может нажать для просмотра деталей. Показывается точное время начала и конца каждого слота.

5. **Бронирование слотa**: Гость нажимает на свободный слот — система мгновенно создает запись о бронировании. На экране появляется уведобление об успешной записи с деталями: тип встречи, дата, время, длительность.

6. **Соответствие длительности**: Длительность бронируемого слота строго соответствует длительности выбранного типа встречи. Если тип встречи задан как «30 минут», слот занимает ровно 30 минут с момента начала.

7. **Запрет на пересечение интервалов**: Система блокирует бронирование, если выбранное время уже занято другим типом встречи. Следующая встреча может начинаться в момент точного окончания предыдущей, но не раньше. Правила действуют и для двух запросов, пришедших одновременно.

8. **Появление записи у владельца**: Только что созданная гостем запись мгновенно появляется в списке запланированных встреч у владельца на его странице. Владелец видит запись с указанием типа встречи, даты и времени.

9. **Обработка одновременных запросов**: Если два гостя попытаются забронировать один и тот же слот одновременно, система обрабатывает запросы последовательно: первый запрос успешно записывает слот, второй запрос получает ответ о том, что слот уже занят, и предлагает альтернативные свободные варианты.

## Установка

<!-- Опишите установку: клонирование, зависимости, переменные окружения -->

```bash
git clone https://github.com/DrPrimus/ai-for-developers-project-386.git
cd ai-for-developers-project-386
hk install --mise   # включить pre-commit хук
```

Запуск фронтенда (порт 80, подробности в `FE/README.md`):

```bash
mise run fe-run
```

Запуск бэкенда:

```bash
mise run be-run
```

Сквозной браузерный тест (Playwright сам поднимает бэкенд и собранный фронтенд):

```bash
mise run e2e-install   # один раз: установить Chromium
mise run e2e
```

Полная проверка проекта, включая E2E:

```bash
mise run check
```

Проверка развёрнутого сервиса по публичному адресу (локальные серверы не нужны):

```bash
PUBLIC_URL=https://<public-url> mise run verify-public
```

Задача сама ставит зависимости фронтенда и Chromium (`fe-install` +
`e2e-install`), отдельный `mise run e2e-install` перед ней не нужен. Скрипт
создаёт тип встречи на `/admin`, бронирует на `/booking` первый слот дня, где
остаётся ещё хотя бы один слот, убеждается, что владелец видит встречу, и
повторяет бронь того же слота через API — ожидается `409` с альтернативами.
Холодный старт развёрнутого инстанса может занимать около минуты, поэтому
таймауты увеличены. При успехе печатается `PASS`, при ошибке — `FAIL` и
ненулевой код выхода.

## Демо

**https://web-production-347f5551.up.railway.app**

Сервис развёрнут на Railway (Free Trial): проект `ai-for-developers-project-386`,
сервис `web`, сборка из ветки `main` по корневому `Dockerfile`, health check —
`/actuator/health`. Пуш в `main` запускает новый деплой.

Trial действует 30 дней или до исчерпания $5 кредита, после чего сервис может
остановиться. Публичная ссылка не вечная — это ограничение бесплатного демо.

В репозитории остаётся и `render.yaml` как альтернатива: Blueprint для Render
собирает тот же `Dockerfile` и проверяет `/actuator/health`. Для создания
сервисов Render сейчас требует платёжные данные, поэтому текущий деплой
выполнен на Railway.

## Render MCP

В корне лежит проектный `opencode.json` с remote-сервером Render
(`https://mcp.render.com/mcp`), чтобы агент мог работать с Blueprint, деплоями,
логами и переменными окружения.

1. Создайте API key: Render Dashboard → Account Settings → API Keys.
2. Экспортируйте ключ в окружение shell/IDE, откуда запускается OpenCode:

   ```bash
   export RENDER_API_KEY=...
   ```

   Ключ не коммитится: в `opencode.json` только имя переменной
   `{env:RENDER_API_KEY}`. Файл `.env.example` — памятка с пустым значением, а не
   рабочий конфиг: OpenCode сам `.env` не читает.
3. Проверьте подключение:

   ```bash
   opencode mcp list   # ожидается ✓ render connected
   ```

   Если выводится `needs authentication` или сервер отвечает 401, проверьте, что
   переменная видна процессу (`printenv RENDER_API_KEY`). После подключения нужно
   один раз выбрать workspace: «Set my Render workspace to <name>».

**Почему не OAuth.** На 2026-11-17 Render не поддерживает dynamic client
registration (DCR) и CIMD и не регистрирует клиента для OpenCode, поэтому
OAuth-вход не завершается. Рабочий вариант — `oauth: false` и API key в заголовке
`Authorization: Bearer {env:RENDER_API_KEY}`. Если ключ попал в чужие руки,
отзовите его в Render и создайте новый.

## Railway MCP

Текущий деплой живёт на Railway, поэтому в `opencode.json` добавлен local MCP
сервер Railway. Он работает через Railway CLI и вашу `railway login`-сессию,
поэтому токенов в конфиге нет.

```bash
brew install railway
railway login
railway mcp install --agent opencode --local   # если нужно настроить заново
opencode mcp list                              # ожидается ✓ railway connected
```

Инструменты позволяют создавать проекты и сервисы, подключать GitHub-репозиторий,
делать деплой, смотреть логи и метрики, управлять доменом и переменными.
Остальные параметры сервиса (`Dockerfile`, health check) задаются через
`railway mcp` или дашборд Railway.

## Docker

Корневой `Dockerfile` собирает один образ: nginx отдаёт собранный фронтенд и
проксирует `/api/` и `/actuator/` в Spring Boot.

```bash
docker build -t ai-for-developers-project-386:local .
docker run --rm -e PORT=8080 -p 8080:8080 ai-for-developers-project-386:local
```

Приложение откроется на http://localhost:8080. nginx слушает `$PORT`, Spring Boot —
внутренний loopback-порт `BACKEND_PORT` (по умолчанию `8081`); Railway и Render
сами передают `PORT`.

Локальная проверка образа — собирает его один раз и запускает на нестандартном
порту и на `8080`, проверяя health, SPA, deep link и API:

```bash
mise run docker-check
```

## Хранение данных

Хранилище в памяти процесса: типы встреч и бронирования не сохраняются на диск и
теряются при перезапуске контейнера и при каждом новом деплое. На Render
free-инстанс дополнительно засыпает после 15 минут простоя, поэтому после
пробуждения данные тоже пусты. Персистентность не добавляется: это осознанное
ограничение учебного демо.
